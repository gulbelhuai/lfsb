# 支付计划生成：补发纳入业务逻辑与实现决策

> 记录时间：2026-08-01  
> 范围：正常发放（`determination_type=normal`）支付计划生成时纳入未发放补发金额  
> 状态：已定稿，供后续迭代对照

---

## 1. 背景与目标

### 1.1 现状问题

- 支付计划明细金额仅取核定明细月标准 `subsidy_standard`，**不含补发**。
- 系统内补发主要来自：
  - **待遇核定** `benefit_determination_item.benefit_amount`
  - **待遇恢复** `shebao_benefit_resume_item.supplement_amount`
- 补发无「是否已发放」状态，无法避免重复纳入或多笔一次发完。

### 1.2 目标

生成支付计划时，发放金额 = **当月金额 + 本期选中的一笔未发补发**；  
前端仍只展示一个「发放金额」，并展示补发所属期起止（有补发时）；去掉「发放年月」列。

---

## 2. 补发数据来源

| 来源 | 表 | 金额字段 | 起止 | 可否纳入条件 |
|------|----|----------|------|--------------|
| 核定补发 | `benefit_determination_item` | `benefit_amount` | 起始=享受开始年月；终止=起始+`benefit_months`-1（仅展示/快照） | `benefit_amount>0`，主表 `approval_status=approved`，补发状态=未补发 |
| 恢复补发 | `shebao_benefit_resume_item` | `supplement_amount` | 已有 `supplement_start/end_month` | `supplement_amount>0`，记录存在即可（**恢复无审核流，有数据即可用**），补发状态=未补发 |

- 金额以库中金额字段为准；核定起止仅作展示/快照，不回算金额。
- 历史存量：系统有未发补发即要发，**不做线下已补清洗**。

---

## 3. 多笔补发选取规则

同一人、**当前支付计划补贴类型**下：

1. **核定优先于恢复**
2. 同优先级按 **补发起始月最早**
3. 再相同：`create_time`、`id` 升序（实现决胜）

约束：

- 每个业务期、每种补贴类型的正常发放计划中，**每个核定明细行最多挂 1 笔补发**。
- 支付计划按补贴类型分别生成，一次生成只查该类型补发，不同类型不冲突。

---

## 4. 补发发放状态机

建议码值：`0` 未补发 / `1` 已纳入支付 / `2` 已发放。

| 时机 | 状态 | 关联字段 |
|------|------|----------|
| 默认 / 历史初始化 | 未补发 `0` | `plan_id`/`detail_id` 空 |
| 支付计划生成或保存选中 | 已纳入 `1` | 写入 `supplement_plan_id`、`supplement_detail_id` |
| 财务审核通过（`finance_approved`） | 已发放 `2` | 保留关联；**银行失败也不回退** |
| **仅撤销**支付计划 | → 未补发 `0` | 清空关联 |
| 复核/审批/财务**驳回** | **不释放** | 仍挂原计划 |

说明：二次发放只汇总历史失败明细重发，**不再挂新补发、不含当月正常补贴**；与「财务通过即已发放」一致。

---

## 5. 支付计划与换绑

### 5.1 同业务期唯一（并发）

同 `determination_type=normal` + `business_period`（自然月月初）+ `subsidy_type` + `del_flag=0`：

- **只允许一条**未删除支付计划。
- 第二人生成/提交：**拦截失败，不改任何数据**。
- 撤销（逻辑删）后可再生成。

### 5.2 重算换绑

关联字段用两个：`plan_id`、`detail_id`（落在核定项/恢复项上）。

对本计划保存/重算时：

1. 将「关联本 `plan_id` 且状态=已纳入」的补发全部退回未补发；
2. 删除旧明细并生成新明细；
3. 再按规则选补发，标已纳入，写入新的 `plan_id`、`detail_id`。

只释放本计划占用的；不动其他计划的已纳入/已发放。

- **允许重算**：待复核、各类驳回（含财务驳回）、草稿等可编辑态。
- **禁止重算**：财务通过后入口禁用。

### 5.3 支付明细落库字段（建议）

| 字段 | 含义 |
|------|------|
| `monthly_amount` | 当月金额（月标准） |
| `supplement_amount` | 本期补发金额（无则 0） |
| `distribution_amount` | 合计（前端主展示） |
| `supplement_start_month` / `supplement_end_month` | 补发所属期快照 |
| `supplement_source` | `determination` / `resume` |
| `supplement_source_id` | 核定明细 ID 或恢复明细 ID |

`payment_month`（发放年月）前端不再展示；库列可保留兼容，写入可置空。

## 6. 与现网模块关系

| 模块 | 关系 |
|------|------|
| 待遇核定 | 审核通过后的 `benefit_amount` 为补发候选 |
| 待遇恢复 | 保存即生效；`supplement_*` 为补发候选 |
| 待遇暂停 | 暂停中（`benefit_status=1`）不进支付计划，与现预览一致 |
| 财务批次 | `finance_approved` 时将本计划已纳入补发改为已发放 |
| 银行发放/失败处理 | 不回滚补发「已发放」；二次发放逻辑独立 |

---

## 7. 实现注意（防回归）

1. 选中补发用条件更新（`status=未补发`），影响行数为 0 则该行不带补发。
2. 撤销释放仅 `status=已纳入`，勿动 `已发放`。
3. `batchInsert` 后需回查明细 ID 再回写 `supplement_detail_id`。
4. 预览与落库选取规则一致，避免「预览有补发、保存没有」或反之。
5. 汇总总金额使用合计后的 `distribution_amount`。

## 9. 对话结论速查

| 议题 | 结论 |
|------|------|
| 候选来源 | 核定已通过 + 恢复有数据；金额>0 且未发 |
| 多笔选择 | 核定优先，再按起始最早 |
| 状态 | 未补发 → 已纳入 → 已发放；仅撤销释放 |
| 财务通过 | 即已发放，不等银行成功 |
| 二次发放 | 只滚历史失败，不带新补发 |
| 恢复审核 | 无审核流，有数据即用 |
| 历史线下已补 | 不考虑，系统有则发 |
| 同月同类型 | 仅一条正常发放计划，第二人失败 |
