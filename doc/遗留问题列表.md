## P0

### ISS-002 待遇认证菜单是空壳：点了显示成功，实际什么都没做

| 项 | 内容 |
|----|------|
| **归属** | 流程一 · 认证 |
| **一句话** | 「待遇认证」页面和接口都在，但业务逻辑没写完；操作员以为认证成功了，系统其实没记任何认证结果。 |
| **操作上会怎样** | 打开认证页能看到列表（还不是真正的待认证名单，而是误用了失地居民列表）。点「认证 / 批量认证」会提示成功，但数据库里没有认证记录，也不会因为「未认证」去暂停待遇。 |
| **技术原因** | 后端 `submit` / `batchSubmit` / `history` 写了 `TODO` 却直接返回成功；前端同样未调真实接口。页面用的状态码（0/1）和字典设计（4月/10月认证等）也对不上。 |
| **影响** | 口述要求一年两次认证、未认证要停发——当前完全无法支撑；还有误导操作员的风险。 |
| **建议** | 要么排期做完整认证（计划导出、导入、未认证联动暂停），要么先把菜单下线并标注「未上线」。 |

## P1

### ISS-005 发放信息修改：改银行卡等关键字段，没有审批，后端也不拦状态

| 项 | 内容 |
|----|------|
| **归属** | 流程一 · 发放信息修改（待遇管理里改银行账号、开户名等） |
| **一句话** | 改已核定人员的发放账户信息时，页面直接保存就生效，没有复核/审批；后端也不检查这条核定是不是「已通过」，理论上草稿/驳回记录也能被改。 |
| **操作上会怎样** | 经办在「发放信息修改」页查人、改银行账号等字段后点保存，核定主表字段立刻变掉，没有第二人确认环节。前端列表一般只展示已通过核定，但若有人绕过页面直接调接口，未通过的核定也可能被改发放字段。 |
| **技术原因** | 没有独立接口，复用待遇核定的 `PUT` 更新；`updateBenefitDetermination` 不校验 `approval_status`。库里虽有 `info_modify` 一类审批角色配置，业务并未接上。 |
| **影响** | 关键发放信息变更缺少审计闭环；与「关键信息要多级审」的期望不一致；错误账号可能直接进入后续支付。 |
| **建议** | 单独做「仅允许已通过核定、只改发放相关字段」的接口；若业务要求审批，再补复核/审批流并写操作日志。 |

### ISS-006 待遇核定：提交/通过/驳回不检查当前该不该做这一步

| 项 | 内容 |
|----|------|
| **归属** | 流程一 · 核定与核定复核 |
| **一句话** | 核定单从草稿到待复核、再到通过/驳回时，后端几乎不看「当前是什么状态」，重复点或乱序调用也可能成功，状态和时间戳会被悄悄覆盖。 |
| **操作上会怎样** | 正常路径：草稿 → 提交复核 → 复核通过/驳回。但若接口被连点或脚本乱调：已通过的单可能再被「驳回」、已驳回的单可能再被「通过」、草稿可能不经页面校验就被标成待复核。页面上不一定拦得住所有情况。 |
| **技术原因** | `submitForReview` 只校验银行卡等字段，不要求当前必须是草稿/已驳回；`approveReview` / `rejectReview` 不要求当前必须是待复核。对比支付计划侧有明确的状态流转校验。 |
| **影响** | 审批轨迹不可靠；并发或误操作会把已生效核定改坏；和支付计划严谨程度不一致。 |
| **建议** | 每一步加「只有允许的当前状态才能变到目标状态」的校验（可参考支付计划 `validateTransition`），更新时带上旧状态条件。 |

### ISS-007 支付计划：二次发放能选但做不了；银行失败后无法在系统里改完重发

> **【已废弃 / 已定稿替代】** 本文条目中的旧口径（失败处理页发起重发、三次封顶等）作废。  
> **现行需求**见 [`doc/二次发放需求.md`](二次发放需求.md)。本条保留仅作历史索引，不再作为实现依据。

| 项 | 内容 |
|----|------|
| **归属** | 流程二 · 支付计划 / 银行发放 |
| **一句话** | （旧）生成计划时界面有「二次发放」选项，一点就报「暂未实现」；银行反馈失败后，失败列表只能看，没有「改信息再发 / 人工处理」的后续功能。 |
| **状态** | 需求已重定：二次发放仅支付计划页入口，从历史 normal 失败明细生成；失败处理页保持只读。 |

### ISS-008 人员信息变更：复核驳回后，不能再新建一条变更单

| 项 | 内容 |
|----|------|
| **归属** | 流程一 · 基本/关键信息变更 |
| **一句话** | 系统认为「只要不是已通过，就算这件事没办完」——包括已驳回。因此驳回后不能再开一张新的变更申请，只能改原来那张再提交。 |
| **操作上会怎样** | 某人有一条变更被驳回后，再点新建变更会提示「存在未完成的业务」。必须找到原驳回单修改后重新提交；不能「作废旧单、另起一单」。 |
| **技术原因** | `hasUnfinishedModifyForPerson` 把除 `approved` 以外的状态（含 `rejected`）都算未办结。 |
| **影响** | 若业务期望「驳回即可新开单」，会被卡住；若期望「驳回必须在原单继续」，则应在页面上写清楚，否则操作员会以为系统坏了。 |
| **建议** | 与业务确认口径：要么驳回后允许新建（未办结不含 rejected），要么 UI 明确引导「请打开原驳回单继续办理」。 |

### ISS-011 教龄补助：在统一「登记复核」里能过/驳，但点详情会报错

| 项 | 内容 |
|----|------|
| **归属** | 流程一 · 登记复核 |
| **一句话** | 教龄登记会出现在统一复核列表里，可以点通过/驳回；但点开详情会提示去教龄模块看，统一复核页看不了明细。 |
| **操作上会怎样** | 复核人在人员复核列表看到教龄待办 → 点详情报错/被拒绝 → 只能自己去教龄补助菜单核对后再回来点通过，流程别扭。 |
| **技术原因** | `PersonReviewServiceImpl` 对 `teacher` 类型在详情接口直接抛「请使用教龄补助模块查看详情」；通过/驳回分支是通的。 |
| **影响** | 复核体验差，易漏核明细就点通过。 |
| **建议** | 在统一复核补齐教龄详情；或列表上对教龄隐藏详情、引导跳转教龄页后再复核。 |
